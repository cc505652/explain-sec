# ExplainSec Phase 2 — Architecture Decision Records (ADRs)

This document records the foundational architectural decisions, rationale, and alternatives considered during the design and implementation of ExplainSec Phase 2.

---

## ADR-001: Single Canonical Firestore `issues` Collection

### Decision
All incidents generated by the telemetry pipeline must be formatted via `buildCanonicalIncident()` and committed directly into the primary Firestore `issues` collection.

### Status
**Accepted**

### Rationale
ExplainSec is built around a single source of truth for incident governance. Writing telemetry incidents to the baseline `issues` collection ensures that SOC L1, L2, IR, Threat Hunters, Managers, SLA Engine, Timeline Engine, and Audit Engine process telemetry-generated incidents seamlessly without requiring duplicate code paths or modified role permissions.

### Alternatives Considered
- **Separate `telemetryIssues` Collection**: Rejected because it would require duplicating every downstream SOC dashboard, routing layer, SLA calculator, timeline generator, and audit logger.

---

## ADR-002: Telemetry Pipeline Boundary at Incident Creation (Human-Centric SOC)

### Decision
The automated telemetry pipeline's responsibility stops strictly at incident creation in Firestore.

### Status
**Accepted**

### Rationale
ExplainSec is an authentic, human-centric Security Operations & Governance platform designed to train and support human security analysts. Automating operational security decisions (such as triage, escalation, containment, or resolution) undermines the educational and operational mission of the platform.

### Alternatives Considered
- **Automated AI Triage & Containment**: Rejected to preserve human analyst decision-making. AI recommendations and automated response playbooks are deferred to future governance phases.

---

## ADR-003: Centralized `TelemetryOrchestrator` Conductor

### Decision
Introduce `TelemetryOrchestrator` as the single execution coordinator for the entire telemetry ingestion, enrichment, classification, detection, campaign, correlation, risk scoring, and incident generation pipeline.

### Status
**Accepted**

### Rationale
Direct coupling between individual pipeline engines creates fragile dependencies and complicates event replay, unit testing, and connector integration. The orchestrator acts as a single conductor coordinating the execution sequence.

### Alternatives Considered
- **Chained Engine Method Calls**: Rejected due to tight coupling and difficulty in pausing/replaying event streams.

---

## ADR-004: Immutable `PipelineContext` Data Container

### Decision
Pass a standardized `PipelineContext` object through each stage of the orchestrator pipeline.

### Status
**Accepted**

### Rationale
Instead of mutating raw telemetry objects or passing loose parameters across functions, `PipelineContext` captures raw input, standardized event, enriched context, classification, detection results, campaign state, correlation results, risk scores, and qualification decisions in a single inspectable object.

### Alternatives Considered
- **Direct Object Mutation**: Rejected because mutating objects in-flight obscures data provenance and introduces side-effects during debugging.

---

## ADR-005: Modular Detection & Correlation Rules Architecture

### Decision
Separate detection rules into `src/telemetry/detection/rules/` and correlation rules into `src/telemetry/correlator/rules/` as independent, modular definitions.

### Status
**Accepted**

### Rationale
Hardcoding detection or correlation rules inside monolith engine classes makes rule management, unit testing, and MITRE mapping updates difficult. Modular rule definitions allow detection engineers to add, modify, or disable rules independently.

### Alternatives Considered
- **Monolithic `switch/case` Statements in Engines**: Rejected due to maintainability and extensibility concerns.

---

## ADR-006: In-Memory `ClusterRepository` Abstraction

### Decision
Abstract correlation cluster storage behind a `ClusterRepository` interface, providing a `MemoryClusterRepository` implementation for Phase 2.

### Status
**Accepted**

### Rationale
Encapsulating cluster state management behind a repository interface insulates the correlation and risk scoring engines from storage details, enabling future seamless upgrades to Redis or Firestore persistence without altering correlation logic.

### Alternatives Considered
- **Direct Global Array Management**: Rejected because un-abstracted memory state complicates state reset during replay and testing.

---

## ADR-007: Seeded PRNG Generator (`seededRandom.js`)

### Decision
Equip the event generator with a Pseudo-Random Number Generator (PRNG) supporting optional seed values (e.g. `seed: 12345`).

### Status
**Accepted**

### Rationale
Automated Playwright E2E tests and live classroom demonstrations require deterministic, repeatable event streams. Seeded randomness ensures that identical seeds yield identical event sequences, classification outcomes, correlation clusters, and incident qualification decisions.

### Alternatives Considered
- **Unseeded `Math.random()`**: Rejected because non-deterministic generation causes flaky automated tests and inconsistent classroom demonstrations.

---

## ADR-008: Multi-Stage Confidence Model

### Decision
Distinguish three explicit confidence metrics: `Event Confidence`, `Correlation Confidence`, and `Incident Confidence`.

### Status
**Accepted**

### Rationale
Raw telemetry alerts possess intrinsic detection confidence from EDR/SIEM providers, while multi-event correlation patterns contribute additional pattern-matching confidence. Separating these metrics makes the final incident risk score explainable to analysts.

### Alternatives Considered
- **Single Global Confidence Score**: Rejected due to lack of explainability.
